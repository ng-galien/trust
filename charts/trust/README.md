# TRUST Helm chart

This chart packages the TRUST browser shell and runtime as one workload. Authentication selects either an external OIDC/OAuth provider or an explicitly configured fixed identity. PostgreSQL remains an external service when selected. Exactly one runtime owns a database; this chart deliberately has one replica, no autoscaler, and `Recreate` upgrades. Planned upgrades have downtime.

## Build and configure

No TRUST image or chart is published automatically. Build the repository image from the repository root using [container instructions](container/README.md), publish it to your authorized registry, and select its immutable digest. The default `trust-server:0.1.0` is a local build name, not a claim that a public image exists.

Set `values.config` using the canonical SDK configuration contract. The mounted file is selected by `TRUST_CONFIG_FILE`; explicit environment values override file values, then defaults apply. `values.schema.json` includes the SDK schema generated by the repository-only `charts/trust/scripts/update-schema.mjs` (run from a built TRUST checkout). The repository's public Helm acceptance verifies that copy against the current SDK export. The chart does not invent a separate set of server configuration fields.

The common values select no provider-specific parameters. A complete authentication configuration is required; a bare chart installation is refused with guidance to the two examples. Replace all example identities and addresses before use. Choose [examples/oidc-values.yaml](examples/oidc-values.yaml) for the `shared` profile with an external HTTPS OIDC/OAuth issuer, the actual access-token audience/profile, and a public browser client with exact login/logout redirects. The example scopes request only selected capabilities; users need their own authorized scopes. Enable explicit extension use scopes only for installed extensions that those users may access.

The OIDC example uses local JWT verification and the issuer's public JWKS. Optional introspection has a separate prerequisite: its canonical `clientSecretReference: {environment, name}` resolves a credential already provisioned in TRUST's runtime credential store. It is not a Kubernetes Secret name or an environment-variable lookup. `secretEnvironment` and `configurationMounts` do not create that TRUST credential. Use the existing authorized credential-provisioning procedure before selecting introspection; this chart introduces no credential bootstrap service.

Put the PostgreSQL connection URL in an existing Secret with key `url`; `secretEnvironment` references it as `TRUST_DATABASE_URL`. Never put database credentials, bearer tokens, client secrets, or a Basic password in values: Helm stores values in its release record, and `config` is a ConfigMap. The chart cannot inspect the content of a referenced Secret. Optional `configurationMounts` reference existing Secrets or ConfigMaps under `/etc/trust-extra/<name>`, for example a private CA named by `NODE_EXTRA_CA_CERTS`, an extension registry, or other canonical file references.

```sh
helm lint charts/trust --strict -f private-installation-values.yaml
helm template trust charts/trust -f private-installation-values.yaml
helm install trust charts/trust --namespace trust --create-namespace \
  -f private-installation-values.yaml --wait --timeout 5m
```

These commands are examples for an explicitly selected target. Acceptance never installs into a retained or enterprise cluster.

The container runs as UID/GID 1000 with a read-only root filesystem, no added Linux capabilities, no service-account token, and writable mounts only for `/tmp` and `/var/lib/trust`. The state PVC retains Operations and local runtime state even when PostgreSQL is external. An existing claim can be supplied. The default requests 10 GiB with the cluster's default storage class. Ensure the storage class supports the requested access mode and fsGroup ownership.

The service exposes the browser shell, which proxies public runtime routes. The runtime port has no separate Service. Ingress is optional; choose the cluster's ingress class, TLS Secret, DNS name and any controller-specific buffering/timeouts needed for SSE and WebSocket traffic. The chart does not silently install an ingress controller, certificate issuer, database, or identity provider.

All probes call the actual `/health` endpoint. It is available after initialization and reports runtime responsiveness; it is not a continuous PostgreSQL or provider readiness check. Dependency failure remains visible through actual requests. Startup has a bounded 120-second probe budget, while graceful termination has 60 seconds by default.

## Fixed identity, including the Runner

Use [examples/fixed-values.yaml](examples/fixed-values.yaml) to select `config.authentication.profile: fixed` and `config.authentication.access.mode: fixed`. Set the exact existing `issuer` and `subject` pair and the complete intended `scopes` array. The issuer is an identity namespace and is never contacted. The example grants only own-Plan reads and Runner execution permissions; add authoring or installed-extension use scopes explicitly when needed. An empty array grants nothing.

The common values contain no OIDC access or browser fields. The fixed example supplies its complete identity directly; no null overrides or knowledge of OIDC defaults is needed. Use one authentication example at a time. The chart embeds the canonical SDK schema and rejects incompatible fields; the runtime applies its strict final configuration validation at startup.

```sh
helm lint charts/trust --strict -f charts/trust/examples/fixed-values.yaml
helm template trust charts/trust -f charts/trust/examples/fixed-values.yaml
```

Customize a copy for installation, including the image digest, database Secret reference, semantic authority and exact UI origins. `allowedOrigins` includes the browser's actual HTTPS ingress origin (or an explicit loopback HTTP origin for port forwarding). Requests with an unlisted Origin are refused. MCP and Runner clients without an Origin need no entry. All admitted clients act as the configured principal; fixed mode does not authenticate individual callers. Keep the Service/Ingress reachable only by the intended users. Existing action scopes, Plan ownership and extension process grants still apply.

The UI opens directly. MCP, RPC and the packaged Runner require no bearer token, login, refresh token, OIDC discovery or credential file. For the Runner, remove an inherited `TRUST_AUTH_FILE` and omit `runner.authFile` from its selected configuration. Point both endpoints at the same TRUST installation, then run one semantic Check URI returned by TRUST:

```sh
unset TRUST_AUTH_FILE
export TRUST_RPC_ENDPOINT=https://trust.example.com/rpc
export TRUST_OTLP_ENDPOINT=https://trust.example.com/v1/traces
node /absolute/path/to/trust/scripts/run.js '<Check invocation URI returned by TRUST>' --json
```

The placeholder must be replaced with the actual URI and its required intentions. Inspect `result.status` and `result.qualification.verdict`; a zero process exit alone does not qualify a Check. This mode changes authentication, not the Runner's public RPC/OTLP execution contract.

When switching an existing installation, preserve its issuer and subject exactly to retain own-Plan access, keep its approved scopes, back up its database/state and perform a controlled restart. Historical Plan creators are never rewritten. The previous OIDC configuration and private credentials can be retained separately for an explicit rollback.

## Storage, upgrades and removal

Use one release per database. `replicaCount` other than 1 is rejected. `Recreate` prevents overlapping Pods during normal Deployment upgrades; Kubernetes can still create a replacement while a manually deleted Pod is terminating. TRUST's database ownership guard is the final refusal boundary, including another release accidentally pointing to the same database. Do not bypass the guard, force-delete a live owner, or scale the release.

Before upgrade, back up PostgreSQL and the persistent state/Operations volume, record the image digest and values, and check compatibility. Published Procedures/Operations and retained Plans must not be reset to resolve incompatibility. There is no general automatic migration promise. Upgrade with the same release, claim and database, allow graceful shutdown, and verify `/health`, the UI, authenticated RPC, and retained Plans afterward.

```sh
helm upgrade trust charts/trust --namespace trust -f private-installation-values.yaml \
  --wait --timeout 5m
helm uninstall trust --namespace trust
```

The default `persistence.retain: true` adds Helm's keep annotation: uninstall retains the PVC. PostgreSQL, external Secrets and provider accounts are not chart-owned. Inspect and back up retained data before any explicit cleanup; retained PVC re-adoption may require an existingClaim setting. A failed upgrade is not permission to wipe data. Secret value changes do not automatically change the Deployment checksum: perform a deliberate rollout after rotating an external Secret.

For explicit persistent PGlite, set `config.storage` to `{kind: pglite, directory: /var/lib/trust/pglite}` and remove the PostgreSQL secret environment entry. Keep the state PVC. A crashed PGlite owner leaves a marker and fails closed: prove no process owns the directory before manually removing its recorded ownership marker. This is an operator recovery step, not an automatic chart hook. PostgreSQL remains the preferred external database for a shared server.

## Package and publication preparation

```sh
helm package charts/trust --destination /tmp/trust-chart-package
helm show chart /tmp/trust-chart-package/trust-0.1.0.tgz
```

Review chart/app versions, image digest, source revision, release notes and actual acceptance results before an authorized OCI `helm push` or index-based publication. Packaging does not publish. No registry destination or credential is embedded in this chart.

## Evidence and limits

The supplied tests are public CLI/Helm/server acceptances; `render.acceptance.test.mjs` invokes actual Helm lint, template, schema refusal and package commands. `runtime.acceptance.test.mjs` starts the actual shell CLI from the rendered container command and ConfigMap, translating only physical mount locations to disposable host directories. It exercises served UI, health, anonymous refusal and authenticated RPC using a maintained OAuth provider over TLS with a disposable private CA. `lifecycle.acceptance.test.mjs` proves actual competing-owner refusal and persisted Plan survival across graceful stop/start on PGlite and PostgreSQL.

`fixed.acceptance.test.mjs` renders the supplied fixed-values example, rejects missing identity/scopes and incompatible OIDC settings, then starts the rendered shell command against disposable PGlite without creating an identity provider. A real packaged Runner executes a Check through that server's RPC and OTLP routes and must receive `COMPLETED / VALIDATED`. This is host execution of the rendered configuration, not evidence of a deployed Kubernetes release.

Record container and isolated Kubernetes smoke observations, image IDs, source revision and command provenance in the durable mission response or private execution records, outside public documentation. A successful render or translated host startup is never reported as an installed cluster workload. Reproduction needs the repository build, Helm, OpenSSL and a disposable PostgreSQL administration connection for the lifecycle assertion; credentials must remain in the private environment. These tests never publish or target a retained database.

Deployment behavior follows the [Kubernetes Deployment contract](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/). Chart schema and packaging follow [Helm chart documentation](https://helm.sh/docs/topics/charts/).
