# Shared server collaboration study — 2026-09-25

This study considers several developers, their agents and their Runners using one central TRUST runtime and one database. The current implementation protects concurrent persisted Plan transitions. It does not yet establish authenticated work ownership or guarantee that two clients cannot perform the same external action. PostgreSQL serialization is a useful foundation for shared work, not a complete collaboration policy.

Baseline: `7d651cce67e1556e6a05d3036a2089dc49854300`. This is a source and architecture study, not behavioral validation. No tests, service probes, runtime changes or account changes were performed. Only this report and the necessary dedicated mission coordination transitions were authorized. Existing unrelated files were preserved. Recommendations below are proposals; open choices remain product decisions.

## What exists, what needs reinforcement, what is absent

| Concern | Current implemented mechanism | Assessment for shared work |
| --- | --- | --- |
| Concurrent database transitions | Composition-root advisory transaction lock, then root row lock; historical children retain the same root lock. | **Existing.** Same composition transitions serialize, including siblings. Independent roots have independent keys; this is not a throughput measurement. |
| Declaration editing | Complete replacement snapshot with `expectedRevision`; mismatch refuses before commit. | **Existing; reinforce UX.** Two clients cannot silently overwrite the same revision, but there is no field merge or participant-aware edit ownership. |
| Chained Check admission | One current intent and one reserved attempt key per Plan. | **Existing.** Competing distinct keys are refused while reserved. This is Plan-level coordination, not a person/agent lock. |
| Unchained Check admission | Attempt-key uniqueness and current-state validation, without a pending Check uniqueness rule. | **Absent general exclusivity.** Two distinct keys can be admitted before either changes the revision. |
| Same-key retry | Pending Attempt can be returned again with the same execution identity. | **Existing transport identity; reinforce execution contract.** Several clients receiving that grant can still perform the external action. |
| Mission ownership | Coordination extension persists designated assignee, claim owner and immutable submitted response. | **Existing domain convention.** Actor is supplied business data, explicitly not an authentication credential. Two hosts using the same assignee are indistinguishable. |
| Session ownership | One open Session per Plan, with expiry and lifecycle state. | **Absent participant attribution.** Session means Plan execution window, not a logged-in user or workstation. |
| Human response | Mobile extension atomically stores the first response to an item; conflicting later answers are refused. | **Existing response integrity; absent respondent identity.** First writer is not necessarily the intended reviewer. |
| Cascades and reads | Child synchronization in the governance transaction; Plan/Check/episode reads use the root scope. | **Existing coherent state.** An already running external action is not cancelled by a later cascade. |
| Live notifications and audit | Process-local bounded event replay plus durable domain records. | **Existing refresh mechanism; reinforce explanation and attribution.** SSE is not a durable actor audit or total commit-order log. |

### Database guarantees stop at the transaction

[`planTransaction`](../../packages/trust-runtime/src/plan/transaction.ts#L4) follows parent links, acquires `pg_advisory_xact_lock` for the composition root and locks its row before invoking the transaction callback. The source therefore implements deliberate application serialization across related Plans; it does not claim SQL `SERIALIZABLE` isolation for every query. [`#createAttempt`](../../packages/trust-runtime/src/plan/runtime.ts#L1526) rechecks the current revision, Session availability, escalations, ancestry and dependencies in that scope. [`#finalize`](../../packages/trust-runtime/src/plan/runtime.ts#L1046) takes the same scope before the Attempt row lock and current qualification work. [`readPlanBySlug`](../../packages/trust-runtime/src/plan/read.ts#L248) assembles its view under the same root scope.

The admission transaction commits before its grant is returned. The Runner then calls [`runOperation`](../../packages/trust-runner/src/check/run.ts#L100), exports Facts and finalizes through subsequent requests. No PostgreSQL lock spans that external execution. An external effect cannot be rolled back by a later `plan-conflict`, and the runtime cannot use its database lock to serialize two workstations' filesystem or HTTP operations.

### Admission is not execution ownership

[`CheckAttemptAdmissionInput`](../../packages/trust-extension-sdk/src/index.ts#L509) carries a Check URI, attempt key and optional intent parameters; it has no participant, workstation or authenticated actor field. [`AttemptStore.createOrFind`](../../packages/trust-runtime/src/attempt/store.ts#L20) deduplicates by `attempt_key`. That means one identity for one logical admission, not one process executing it.

For an intent-chained Plan, [`bindIntentAttempt`](../../packages/trust-runtime/src/plan/store.ts#L201) requires both reservation fields to be empty and binds one key to one Check at the expected revision. A different key fails with `intent-in-use` ([runtime mapping](../../packages/trust-runtime/src/plan/runtime.ts#L864)). Even independent Checks in that Plan share this reservation. Separate child Plans have separate intent state, though their database transitions still share the root lock.

For an unchained Plan, [`#createAttempt`](../../packages/trust-runtime/src/plan/runtime.ts#L1560) checks an existing key and only applies intent reservation when chaining is enabled. Admission itself does not advance the Plan revision. Distinct keys admitted sequentially under the lock can therefore both receive grants for the same still-open Check. Conversely, [`#resolveAdmission`](../../packages/trust-runtime/src/plan/runtime.ts#L1312) deliberately accepts an existing pending key when its identity/context remain valid; [`#createAttempt`](../../packages/trust-runtime/src/plan/runtime.ts#L1560) returns that pending Attempt. The normal packaged Runner generates a fresh UUID per invocation ([Runner source](../../packages/trust-runner/src/check/run.ts#L59)), but the public admission contract supports callers reusing a key. There is no server-side execution-start ownership exchange.

Fact and Snapshot deduplication solve a different problem. [`fact`](../../packages/trust-runtime/src/plan/runtime.ts#L1728) derives identity from Check/compiled definition/Operation/index/**observedAt**/values, and [`FactStore.append`](../../packages/trust-runtime/src/fact/store.ts#L30) reconciles identical persisted content and rejects collisions. Two actual executions generally have different observation instants, so equal business values alone do not make them identical Facts. Even exact Fact replay does not undo a duplicated external action. A second finalization for an already satisfied live Check is refused ([runtime](../../packages/trust-runtime/src/plan/runtime.ts#L1112)); its external action may already have happened.

### Claims, declarations and Sessions

The coordination Procedure binds the Operation's `actor` input to immutable `assignee` and qualifies returned ownership ([Procedure](../../assets/procedures/agent-delegation.feature#L38)). Its external [`mission_claim`](../../environments/trust-test/manifests/postgres/002-missions.sql#L60) locks the mission row, checks the supplied actor against the designated assignee and changes pending to claimed. The SQL explicitly calls these actor values trusted-host correlations, not authentication credentials ([comment](../../environments/trust-test/manifests/postgres/002-missions.sql#L22)). Repeating the same actor does not acquire a distinct worker identity, and there is no generic core Plan claim, reassignment, takeover or claim-expiry policy. This extension's ownership does not authorize arbitrary access to another Plan in core admission.

Declaration replacement is a complete snapshot with `expectedRevision` ([public contract](../../packages/trust-extension-sdk/src/index.ts#L456)). Both unchanged and changed replacements recheck the revision under the root lock ([unchanged](../../packages/trust-runtime/src/plan/runtime.ts#L644), [changed](../../packages/trust-runtime/src/plan/runtime.ts#L730)). A live chained reservation additionally prevents changed declarations. An unchained in-flight Attempt has no corresponding declaration freeze. A conflict should make the editor reread and present the intervening changes; blindly resending a stale complete snapshot at the new revision could intentionally overwrite somebody else's unrelated edits.

[`Session`](../../packages/trust-runtime/src/model.ts#L130) stores only ID, Plan, state and timestamps; [`one_open_session_per_plan`](../../packages/trust-runtime/src/database/postgres-schema.ts#L146) enforces one shared execution window. [`close`](../../packages/trust-runtime/src/plan/runtime.ts#L339) closes that Plan's open Session, so one caller can affect another caller's pending work. Expiry/renewal releases stale intent reservations ([runtime](../../packages/trust-runtime/src/plan/runtime.ts#L1600)). The Runner checks expiration before starting, but an external action already running is not stopped simply because this Session closes or expires. Incoming Facts require an unexpired Attempt and open Session ([ingestion](../../packages/trust-runtime/src/plan/runtime.ts#L947)). A replacement attempt can thus overlap an old external execution after its governance eligibility has ended.

Intent text describes the next governed action, not the authenticated author or a liveness heartbeat. First Plan read can initialize it ([reader](../../packages/trust-runtime/src/plan/read.ts#L257)); successful qualification rotates it, negative qualification releases the reservation without advancing it. Shared UI should label these as shared Plan intentions and execution state, not “Alice is currently working” without separate evidence.

### Human response attribution

The mobile companion provides a concrete existing human-response path. [`responses.submit`](../../extensions/mobile-companion/server.mjs#L1252) accepts only `item`, `expectedRevision` and `answers`; expected revision must be zero. It inserts one response per item and stores answer fields in the same transaction. Identical replay returns the stored response; differing answers produce a conflict. [`getResponse`](../../extensions/mobile-companion/server.mjs#L285) returns item, form/response revisions, timestamp and answers, with no respondent identity. The [decision-read Operation](../../extensions/mobile-companion/operations/mobile.response-decision-read.feature#L12) produces item, decision and the two revisions, with no person attribution either.

Consequently, first-response integrity and form qualification exist, but neither identifies the intended reviewer. The open decision is whether a response belongs to an individually assigned reviewer, any authorized collaborator, or an explicitly shared group. If individual attribution is required, it must originate at the human submission boundary and survive into the Operation's Produced shape/Procedure criteria where relevant. A caller-supplied display name, Plan Session ID or Runner execution ID alone cannot establish who answered. This study does not choose an account provider or change the extension contract.

### Cascades, notifications and useful history

[`#finalize`](../../packages/trust-runtime/src/plan/runtime.ts#L1126) invalidates dependent Check observations; [`synchronizeChildren`](../../packages/trust-runtime/src/plan/children.ts#L216) follows the composition and can supersede a child whose canonical comparison fingerprint or eligibility changed ([generation decision](../../packages/trust-runtime/src/plan/children.ts#L293)). Historical records remain meaningful, while current qualification can change. Finalization checks current compiled semantics/dependencies and the captured child invocation digest ([runtime](../../packages/trust-runtime/src/plan/runtime.ts#L1083)). These guards prevent a stale action from qualifying a changed context; they do not cancel that action or restore its external target.

[`PlanEvents`](../../packages/trust-runtime/src/plan/events.ts#L7) retains 1,000 process-local events, using a generation and sequence, and requests resynchronization for an unknown/out-of-window cursor. [`SSE`](../../packages/trust-runtime/src/http/events.ts#L9) sends replay and future notifications. The [UI subscriber](../../packages/trust-ui/src/lib/plan-events.ts#L10) treats these as invalidation hints and falls back to polling while disconnected. Finalization publishes ancestor changes and its revision event after commit ([runtime](../../packages/trust-runtime/src/plan/runtime.ts#L1283)); asynchronous publication should not be treated as a durable total ordering of database commits. A current read, not event arrival order, establishes current Plan state. A client watching a child affected by a different Plan's cascade needs explicit acceptance coverage for refresh visibility.

Durable revisions, Attempts, receipts, Facts, Snapshots and escalations already answer which governed context, observations and verdicts existed. Coordination also records claimed/completed actor strings in its own mission events. Missing for shared-user attribution are a trusted initiator for declarations, Session lifecycle, Attempt admission and operator resumption, plus a distinction between human principal, dispatched agent and actual Runner process. Denied calls do not create an Attempt row in the examined refusal path, and SSE does not retain every denial. Useful future audit should capture these distinctions and correlation IDs without persisting credentials, whole delegated Environments or unnecessary personal data. The existing domain history should remain the qualification authority; an audit addition should explain actions rather than duplicate it.

## Concrete collision journeys inferred from source

These are predicted paths for future public acceptance, not scenarios executed in this study.

1. **Two developers edit one declaration snapshot.** A and B read revision 10. A replaces it and commits revision 11. B submits `expectedRevision: 10` and receives `plan-conflict`; B must reread and consciously reconcile. A no-op replacement still checks the expected revision. There is no automatic merge.
2. **Two ordinary Runners choose one unchained Check.** A and B each generate a different key. A's admission transaction commits while the Check remains open; B is admitted at the same revision. Both invoke a mutating external Operation. A's accepted Facts qualify it; B's finalization is refused if it is now satisfied. Persistence is consistent even though the external action occurred twice.
3. **Two ordinary Runners choose a chained Check.** A reserves the Plan's current intent; B's different key is refused before its Operation runs. This also prevents B from concurrently choosing another Check in the same Plan. It does not identify A as a particular developer. A duplicated client using A's pending key can receive the same grant; that is a separate collision path.
4. **A slow action outlives its Session.** A starts an external action; its Session expires or another caller closes it. A later engagement/resumption path can supply a fresh execution window and release a stale reservation. B may start another attempt while A's external process still runs. A's newly submitted Facts are rejected on expiry/closed Session. There is no generic external cancellation/fencing guarantee.
5. **A sibling result changes while another action runs.** Database finalizations serialize at the shared root. The later finalizer evaluates current dependencies/generation, preserves valid history and refuses stale qualification where applicable. The losing Runner's external effect remains outside that protection. UI should explain the changed ancestor/child context rather than merely showing an unexplained failure.
6. **Two humans answer one mobile item.** Both submit expected revision zero with different answers. Only one response is persisted; the second receives a conflict. Current history identifies the item and answer, not which human won. An immutable response prevents overwriting but cannot establish reviewer authority.

## Open product decisions and bounded recommendations

1. **Ownership scope:** is collaboration organized by a whole Plan, child mission, or Check? Keep extension business assignment distinct from authenticated caller attribution. Decide whether a trusted-host convention is sufficient for the first central deployment or whether named participants must be enforced at public boundaries. Do not describe the current mission claim as user authorization.
2. **Admission policy:** decide whether ordinary live Checks should reject a second pending distinct key independently of intent chaining. Preserve intentional concurrency between different Checks and child Plans where the Procedure allows it. Specify same-key re-admission separately: a repeated grant is not permission to assume external execution has not started.
3. **External-effect policy:** retain the established replay model. For important mutating Operations, author a domain idempotency key or reconciliation/read-back where the target supports it. For an unknown outcome that cannot safely be repeated, route to explicit human intervention. A generic database-backed exactly-once engine is neither required nor implied.
4. **Handoff and expiry:** decide who may close/resume a shared Plan Session, replace declarations, take over a mission and acknowledge an unknown external outcome. Show pending/expired/interrupted/accepted states and the relevant initiator. Avoid representing expiry as proof that a process stopped.
5. **Human decisions:** choose intended reviewer scope and how verified respondent identity reaches response history and, if qualification needs it, Fact fields. Preserve current first-response conflict semantics unless the owner explicitly chooses a revision/amendment model.
6. **Shared visibility:** show current revision, shared intent reservation and any trusted participant information separately. On conflict, refresh and present what changed before proposing a replacement. On a cascade, identify affected dependencies. On event reconnect, reread canonical state.

## Future public acceptance matrix

Existing tests are source evidence only here. [`runtime-invariants`](../../packages/trust-runtime/acceptance/runtime-invariants.acceptance.test.ts#L210) covers intent rotation and competing admissions; its [same-key concurrency journey](../../packages/trust-runtime/acceptance/runtime-invariants.acceptance.test.ts#L911) exercises RPC admission/finalization identity, not two real external executions. [`storage-concurrency`](../../packages/trust-runtime/acceptance/storage-concurrency.acceptance.test.ts#L21) covers concurrent publication/engagement/Fact replay and [distinct Check finalization](../../packages/trust-runtime/acceptance/storage-concurrency.acceptance.test.ts#L123). No earlier pass result is claimed as validation of this study.

| Future journey | Public surfaces and observable assertions |
| --- | --- |
| Competing declaration editors | Two RPC/MCP clients read one revision, replace different complete snapshots; one wins, the other gets a stable conflict, no partial state; UI rereads before retry. |
| Two distinct Runner keys, same live Check | Two real packaged Runners and a disposable controlled external target; count effects as well as Attempts/Facts/verdicts. Cover chained and unchained Plans against the chosen admission policy. |
| Same-key concurrent admission | Public RPC returns one pending identity; controlled clients show the separate external-execution question. An eventual policy must explicitly define whether repeated grant delivery can cause repeat execution. |
| Session close/expiry during an action | Hold a disposable external Operation in progress, close/expire its Session via public paths, then release it. Check late Facts, reservation release, new attempt admission and external effect count independently. |
| Independent Checks/child missions | Distinct clients run eligible independent work; preserve both qualifications and monotone revisions while child/root reads remain coherent. Do not accidentally turn a Check-level policy into a global server lock. |
| Child cascade during admitted work | One client changes a qualifying prerequisite/result while another waits in an external action. Assert stale finalization refusal, historical Facts where accepted, replacement generation and current UI refresh across both child and parent views. |
| Human reply race and attribution | Two intended identities submit differing answers to one disposable item; verify one immutable answer and a conflict. Once attribution policy exists, assert the recorded/qualified responder comes from that boundary, not user-controlled prose. |
| Mission claim/handoff policy | Separate authenticated participants/agent dispatches attempt the same assignment; assert the chosen owner/takeover policy and its audit. Current identical-assignee replay alone cannot prove distinct worker exclusion. |
| Notification reconnect/cursor overflow | Use public event stream and reads, miss events or reconnect with an out-of-window cursor; assert resync and current state without relying on notification sequence as the revision authority. |
| Audit correlation | Trace a public admission, refusal, declaration conflict and operator resumption to the correct participant/agent/Runner under the chosen identity design; exclude delegated secrets from records. |

The first decisions needed are participant attribution, ownership scope and the pending-admission policy. Existing transaction serialization, revision checks, immutable history and domain-specific replay safeguards can support those decisions without changing the one-runtime-per-database architecture.
