# Minimal ABAC and identity integration for shared TRUST

Status: ABAC and proof workflow authorized, external OIDC identity and browser flow approved, 2026-09-26. No native TRUST user/password/session/token issuer. The server selects local JWT validation or OAuth introspection on each request. Literal OAuth scopes carry permissions. Implementation is authorized; no universal five-minute policy is imposed. No deployment or runtime activation is authorized by this document. One runtime owns each database; multiple users, workstations, agents and Runners connect to it.

This specification supersedes all `standard`/`extended` and Observer/Operator/Coordinator/Author/Admin proposals in the earlier shared-server studies. Those names are not product roles. It also supersedes token-owned Plans: the owner's explicit 2026-09-26 decision is ownership by stable external principal, identified by issuer and subject. Professional multi-user use is the context, not a delivery deadline. Existing studies describe historical evidence, not current requirements.

## Fixed authorization rule

An authenticated, active principal may invoke an action only when that exact resource action is in its effective permissions. Unknown actions and missing permissions are denied. Effective permissions must remain within the account ceiling under the explicitly agreed freshness contract; local JWT validation alone cannot establish instantaneous current permissions. There is no generic policy language or configurable role catalog.

Plan actions also require scope `own` or `all`. With `own`, the verified principal's `(issuer, subject)` must equal the Plan's immutable creator reference. A refreshed or newly issued token for that same principal does not create a new owner or an automatic delegation. With `all`, the equality restriction is removed; every existing permission and domain precondition remains. A child inherits its root Plan's creator principal. An unattributed historical Plan is visible only under `all` until an explicit attribution operation is approved and implemented; no creator is inferred.

Attempts record the acting principal separately from the Plan creator. Taking over work preserves the creator and existing history. Token/client identifiers may be audited separately; they are not an ownership boundary. Refresh alone must not prevent the same authorized principal from continuing. Admission, Facts and completion must remain correlated with the authenticated actor and existing Attempt context. A Plan never stores a bearer credential.

The external provider issues the permission; the extension never grants itself access. Core Plan operations still require their independent exact action and own/all scope. Core publication, credentials and extension lifecycle permissions also remain independent. Fine permissions declared by extensions are a possible later evolution, not a second implemented model.

## Identity and transport design

The configured external provider owns human/service accounts, login, credentials, groups and lifecycle; TRUST retains minimal external identity references for attribution. The approved browser flow is a public SPA client using Authorization Code with PKCE S256 and the maintained provider-neutral oidc-client-ts client. Access and refresh tokens exist only in browser memory, never localStorage, sessionStorage or IndexedDB. A public client has no client secret. Each protected request sends its access token. Reload may return through provider SSO without another password when the provider session permits; silent SSO is not guaranteed in every browser. Browser authentication stays separate from execution Sessions. A BFF is a future alternative if stronger token isolation or operational requirements justify it, not the selected architecture. Internal deployment still requires HTTPS and attention to script/extension trust, especially for Trial and credential permissions.

Each protected request presents an access token, not necessarily a newly issued one. TRUST verifies identity and effective permissions for that request. Being the creator does not exempt a principal from action permissions. Removed necessary permissions prevent subsequent work once that change is effective under the agreed freshness contract; additional permissions permit only their corresponding actions and scope. JWT signature/expiry verification alone cannot discover new Keycloak permissions or removals. Do not claim that active-token introspection automatically recalculates embedded rights. The server configures local JWT verification or provider introspection on every protected request. Strict introspection has no positive decision cache and never silently falls back to offline verification; outages deny access. JWKS caching is distinct from decision caching. Provider-specific invalidation and permission-change behavior must be tested, not assumed. No database lock spans external execution, and revocation cannot undo an already launched external action.

Adapters establish a server-owned actor context. Request arguments, display names, `published_by`, mission assignees and declared agent names do not authenticate it. RPC batch items each require authorization. MCP aliases share the same decision. OTLP must correlate accepted Facts with the authorized acting principal and Attempt. Long-lived event streams recheck authority according to the agreed freshness contract and cannot leak other Plans on reconnect or effective revocation. Extension projections, proxy reads/commands, diagnostics and LSP must not bypass the same boundary. Features lacking a safe authorization mapping fail closed in shared mode until covered.

The Runner reads credentials from private storage, outside compiled JS and command arguments, and sends access tokens only to the configured TRUST origin. It must not forward them to external actions or spawned shell environments. Different tokens for the same principal can carry different rights; permissions are never unioned across tokens. They nevertheless identify the same creator. Authentication transport must preserve the existing one-semantic-Check-URI invocation contract.

## Implementation ownership

A dedicated access component owns authentication AND rights decisions, registered in the existing Awilix composition root (`packages/trust-runtime/src/runtime.ts`, `createContainer` with explicit registrations). Inject trusted issuer configuration, verifier/JWKS client and clock through the container; do not resolve the container from runtime services or construct verifiers independently inside transports. A shared singleton verifier may retain safe key caches, never a mutable current principal. Each request receives a separate immutable authenticated context, explicitly passed to authorization. Match the existing singleton service pattern. Separate token validation from Plan/action authorization internally, while retaining one application authority for access decisions. Transports are thin adapters and must not duplicate permission logic; existing business prerequisites remain in their domain services. Tests replace injected dependencies and interleave two principals across transports to detect identity leakage. This is an in-process service, not a new deployment container.

Canonical public access contracts belong to `trust-extension-sdk`, exhaustive union matchers to its `/match` entrypoint. Verified token intake and server-owned actor context belong to `trust-runtime`; external account/credential ownership must follow the final identity decision. Shared Plan authorization and attribution belong beside the existing Plan/Attempt services and stores. PostgreSQL and PGlite share schema and constraints. Runner credential handling belongs to `trust-runner`; deployment settings use the common shell. UI consumes public contracts.

Upgrade work is explicit and data-preserving. No retained runtime, DB or services are reset or upgraded as a side effect. Prepare and test upgrades/restores on verified copies; retain original historical Plans and nullable unknown creator attribution. No compatibility adapter or generic migration framework is implied.

## OIDC and accountable principals: added scope

The user explicitly requested a tested Keycloak SSO scenario, with Google brokered upstream. The browser is the OIDC client and TRUST is the API resource server; it need not receive or retain Google credentials. Authorization Code with PKCE S256, state and nonce is the approved human sign-in flow. Validate issuer, signature, audience, expiry and transaction correlation; bind a person by verified issuer and subject, never by a client-supplied name or an automatic email merge. Successful SSO alone grants no additional TRUST permissions.

Distinguish a human developer, a service principal acting in its own name, and an agent using a limited token for a developer. A Keycloak client-credentials access token represents the service principal; an ID token is not an API access token. Preserve responsible principal, credential identity, acting principal, and immutable Plan creator in audit. These identities do not introduce organizations, tenancy or shared human accounts.

Test with an isolated provider/realm. Do not access enterprise Google/Keycloak or request production secrets. A real Keycloak broker can be tested against a disposable upstream OIDC provider; that proves broker interoperability, not an actual Google enterprise login. Final real-provider validation needs the approved issuer/realm, application public URL and exact callback/logout URLs, client identifier and authentication method, accepted audience, permission-claim mapping, allowed human/service identities, and revocation/logout contract. Secret provisioning remains out of source and reports.

Approved provider-neutral configuration: explicit trusted issuer(s), API audience, validation mode, relevant timeouts/lifetime/skew, and public SPA client/redirects. Discover standard endpoints only from configured issuers and require exact issuer consistency. Never discover a token-supplied arbitrary issuer. Introspection is OAuth RFC 7662, only available when the provider supports it. Confidential credentials use existing server-side secret references and never enter public browser configuration. Keycloak/Google is an integration scenario, not a hardcoded runtime dependency.

Primary references: [Keycloak OIDC endpoints and flows](https://www.keycloak.org/securing-apps/oidc-layers), [Keycloak identity brokering and service accounts](https://www.keycloak.org/docs/latest/server_admin/), [Keycloak authorization services](https://www.keycloak.org/docs/latest/authorization_services/).

## Server-selected validation and development

Server configuration selects `local-jwt` or `introspection`; clients cannot change that selection. Local JWT verification validates the signature and configured issuer/audience/time/algorithm on every request. The provider mode calls the configured standard introspection endpoint on every protected request, with no positive decision cache or silent fallback. It validates active state and required metadata and then applies the same action/resource rules. It does not promise recomputation of current account rights unless demonstrated by that provider. Revocation, logout, disablement and permission withdrawal have separate assertions. JWKS caches remain allowed and distinct from permission-decision caches.

Document recommended defaults (initial candidate access lifetime 300 seconds, clock tolerance 30 seconds, bounded provider timeout) as configurable settings, not fixed product requirements or guarantees of immediate revocation. The local mode's effective withdrawal window includes provider propagation plus the final stale token's remaining accepted lifetime and clock tolerance. The online mode's semantics follow measured provider behavior.

Use the standard OAuth `scope` string with literal values such as `trust.plan.read.own trust.check.attempt.admit.own trust.procedure.publish`. A closed table maps values to canonical actions and, for Plan-bound actions, `own` or `all`. No wildcard, custom permission JSON or TRUST role catalog. Unknown scopes grant nothing; missing required permissions and malformed claims refuse. Configure provider issuance to respect account/client/grant limits and test refresh. Verify stable access-token subjects across browser, Runner and MCP clients rather than assuming cross-client ownership.

Daily development must not require Keycloak, an enterprise provider or a container stack. Select a maintained lightweight OAuth/OIDC test provider with genuine signed tokens/JWKS and standard flows; use the same Awilix validation and rights authority as shared mode. An explicit local profile and private token-acquisition/injection helper serve Runner/API development without printing credentials. Browser tokens remain in memory. The development provider is test tooling only, not a production TRUST issuer. Keycloak remains optional for full interoperability; actual Google integration remains separate evidence.

Controlled signed test issuers, clocks and network dependencies may be injected through the composition root for deterministic tests. No accept-any token, unsigned bearer or authoritative user header bypass is permitted. Shared configuration rejects accidental development defaults/test wiring; endpoints come from explicit trusted configuration/discovery. Confidential secrets stay out of public SPA configuration. Runtime startup does not alter retained services.
