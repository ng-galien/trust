Le `Background: Plan context` déclare d'abord le périmètre d'action de la Procédure, puis chaque valeur qu'un Plan porte sous forme de **rôles** typés et nommés. Des Checks et des Invocations enfants terminées peuvent remplir des rôles observés ; aucun ne modifie les entrées initiales immuables.

> La première DataTable définit les limites autorisées et interdites. Chaque phrase suivante déclare un rôle, avec son type, sa cardinalité et sa source.

```gherkin fragment title="Un rôle par ligne"
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all   | Change and verify only the declared project. | Alter the environment to make a Check pass. |
    And one reference "jira issue"
    And many reference "affected project" declared optionally by agent for "jira issue"
    And many reference "fix revision" for each "affected project"
    And one reference "acceptance project" fixed as "payment-acceptance"
```

## La phrase

```gherkin fragment
Given|And one|many string|number|instant|reference "<role>" [declared [optionally] by agent] [fixed as "<value>"] [returned] [for "<parent>"]… [for each "<parent>"]…
```

| Partie | Règle |
| --- | --- |
| `Given` / `And` | l'un ou l'autre mot-clé après la DataTable obligatoire de périmètre ; aucune autre table ni doc string |
| `one` / `many` | cardinalité : un scalaire, ou une collection du type |
| `string` `number` `instant` `reference` | les quatre mêmes types que les Inputs d'Opération et les champs produits |
| `"<role>"` | nom libre entre guillemets, non vide, unique dans la Procédure — un libellé lisible (`"jira issue"`, `"fix revision"`), pas un identifiant |
| `declared by agent` | l'agent fournit la valeur après l'engagement |
| `declared optionally by agent` | l'agent peut omettre la valeur ; lorsqu'elle est fournie, les mêmes règles de type et de cardinalité s'appliquent |
| `fixed as "<value>"` | la valeur est écrite ici ; seulement pour `one string` ou `one reference` ; ne se combine pas avec `declared by agent` |
| `returned` | expose comme Result de cette Procédure un rôle produit par un Check validé ou une Invocation enfant ; ce n'est ni une entrée, ni une valeur fixe, ni une déclaration de l'agent |
| `for "<parent>"` / `for each "<parent>"` | rattachement à un rôle parent, voir plus bas ; répétable, combinable avec les deux clauses ci-dessus |

## Les cinq sources

La source d'un rôle découle de ses déclarations et du Check ou de l'Invocation qui le produit. `returned` annote un rôle observé ; ce n'est pas une sixième source.

| Source | Comment | Remplie | Exemple |
| --- | --- | --- | --- |
| **Valeur fixe** | `fixed as "<value>"` | par la Procédure elle-même | `And one reference "Kind cluster" fixed as "trust-test"` |
| **Déclaration de l'agent** | `declared by agent` | après l'engagement, par l'agent, via l'opération de déclaration fermée | `And many reference "affected project" declared by agent for "jira issue"` |
| **Champ matérialisé** | un Check de la Procédure `materializes "<role>" from field "<field>"` | par ce Check, à partir d'un de ses champs produits, une fois validé | `And one reference "baseline revision" for "project"` + `… and materializes "baseline revision" from field "headRevision"` |
| **Result d'Invocation** | une Invocation `materializes "<role>" from Result "<child role>"` | depuis le Plan enfant courant entièrement validé ; retiré s'il perd sa validation | `And one reference "child revision"` + `… and materializes "child revision" from Result "revision"` |
| **Entrée de Plan** | aucune des précédentes | à l'engagement, par qui engage le Plan (entrées racines) | `Given one reference "repository"` |

L'engagement accepte **exactement** les entrées de Plan — aucun rôle fixe, déclaré ou matérialisé. Ajouter une clause `materializes` sur un Check ou une Invocation transforme ce qui aurait été une entrée de Plan en rôle dérivé.

## Rattachement à un rôle parent

`for "<parent>"` et `for each "<parent>"` rattachent un rôle à un autre rôle : une révision appartient à un projet, une heure d'enregistrement appartient à un document.

- Le parent doit être un rôle déclaré ; les relations de parenté forment un graphe acyclique.
- Un rôle sous une déclaration facultative de l'agent doit lui-même être déclaré facultativement par l'agent, ou être matérialisé par un Check ou une Invocation. Cela empêche une valeur obligatoire de dépendre d'un parent que l'agent peut omettre.
- `for "<parent>"` : une valeur parente partagée. `for each "<parent>"` : une valeur par valeur du parent. La relation retient **quelle valeur appartient à quel parent**. Quand un Check s'exécute `on each "affected project"`, un `using "fix revision"` sélectionne la révision de *ce* projet, pas la collection entière. La sélection suit le rattachement, jamais une position dans un tableau.
- Deux rôles sont dans le **même périmètre** quand l'un est `for each` l'autre, ou quand ils partagent les mêmes parents. Ce périmètre commun permet à un rôle `many` d'alimenter un Input `one` sous `on each`, à un scalaire produit d'être comparé avec `context["<many role>"]`, et à un champ scalaire de matérialiser un rôle `many`.

```gherkin fragment title="Extrait de la Procédure de départ d'avion : valeurs rattachées à un vol"
    Given one reference "flight"
    And one reference "aircraft" for "flight"
    And many reference "cabin item" declared by agent for "flight"
```

## Ce qu'un rôle alimente

- **Une cible de Check** : `on "<role>"` — un Check (`on "project"`), un Check par valeur (`on each "affected project"`), ou un Check avec la collection entière (`on all "…"`).
- **D'autres Inputs** : `using "<role>" as Input "<input>"` (`using all` pour une collection).
- **Une référence de qualification** : `context["<role>"]` lit la valeur d'un rôle visible du Plan — voir [Qualifications](/docs/procedures/expectations).

Types et cardinalités doivent correspondre à l'Input de l'Opération à chaque liaison : un rôle `many reference` ne peut pas alimenter un Input `one` sans `each` ; un rôle `string` ne peut pas alimenter un Input `reference`.

<Details title="Rôles compilés" expert>
Chaque rôle compile en `{ name, type, cardinality, source, parents: [{ role, each }] }` où `source.kind` vaut `plan-input`, `agent-declaration`, `fixed` (avec `value`), `operation-field` (avec Check et champ), `invocation-result` (avec Invocation et Result), ou `plan-identifier` (le rôle synthétisé `plan`, voir [Scénarios et Checks](/docs/procedures/scenarios-and-checks)). Un Result porte aussi `returned: true`. La page de la Procédure liste les entrées de Plan dans son inspecteur ; le formulaire d'engagement d'un Plan est généré à partir d'elles.
</Details>
