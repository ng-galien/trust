## Transmettre des Results vérifiés entre Plans

Les Inputs du parent vers l'enfant sont explicites et figés pour chaque génération enfant. Dans l'autre sens, la Procedure enfant marque un rôle observé `returned` ; l'Invocation parente relie explicitement ce Result à l'un de ses propres rôles typés. L'enfant n'écrit pas arbitrairement les variables du parent et ne modifie pas ses entrées racines immuables.

```gherkin fragment
  # In the child Procedure's Plan context and producing Scenario:
  And one reference "revision" returned
  Then Check "read revision" runs Operation "git.head-read@1.0.0"
    on "repository" as Input "project"
    and materializes "revision" from field "headRevision"
    and must establish "the revision is observed"
    """js
    fact.workingTree === "clean" || fail("the working tree is not clean")
    """

  # In the parent Procedure's Plan context and child Scenario:
  And one reference "child revision"
  Then Invocation "observe child" runs Procedure "result-child@1.0.0"
    on "repository" as Input "repository"
    and materializes "child revision" from Result "revision"
    and must establish "the child observation is complete"
```

Le compilateur refuse un Result absent, non marqué `returned`, incompatible ou fourni plusieurs fois. Un Result enfant sans rattachement peut alimenter un rôle parent sans rattachement ; `on each` peut relier un Result par cible à un rôle parent `for each` correspondant. Les autres topologies de Result ne sont pas encore prises en charge. Pour une collection de missions déclarées, la cible parente est un rôle `many` sans rattachement et le contrat de Result de chaque Procedure enfant proposée est vérifié avant l'acceptation de sa mission.

Seul le **Plan enfant courant entièrement validé** fournit ses valeurs de Result. Une nouvelle observation validée les remplace dans une nouvelle révision du parent. Si l'enfant est requalifié négativement, escaladé ou si sa génération est remplacée, TRUST retire ces valeurs et rouvre les Checks parents dépendants ; les enfants sans lien gardent leur identité. `plan.read` expose les `importedResults` courants avec la provenance de l'enfant et de sa génération ; les révisions conservent leurs projections antérieures. Aucun hook ni qualification indépendante de l'Invocation n'intervient.

## Collections de missions dynamiques

Une Procedure peut exposer des collections de missions qu'un agent remplit après engagement. TRUST valide chaque mission et fige sa composition complète avant de créer son Plan enfant. Chaque enfant possède ses Checks, sa Session et son historique. Une collection vide attend du travail.

Ces Procedures complètes déclarent la collection parente et le Check exécutable du worker. Celui-ci exige l'Operation installée `git.head-read@1.0.0` et un dépôt accessible au Runner dans un Environment compatible. Le Check qualifie l'état observé du dépôt, pas le rapport du worker.

```gherkin procedure id="dynamic-mission-parent"
@trust-dsl:1 @procedure:documentation-missions @version:1.0.0
Feature: Govern declared repository observations
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all | Read assigned repositories. | Modify repositories or launch unassigned work. |
    And missions "work" declared by agent
  @scenario:work
  Scenario: Execute declared missions
    Then Invocation "execute-work" runs each declared Procedure in "work"
      and must establish "the declared observations are complete"
```

```gherkin procedure id="dynamic-mission-worker"
@trust-dsl:1 @procedure:documentation-observation @version:1.0.0
Feature: Verify a delegated repository is clean
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all | Read the assigned repository. | Modify the repository or qualification criteria. |
    And one reference "repository"
  @scenario:observe
  Scenario: Observe the repository
    Then Check "clean repository" runs Operation "git.head-read@1.0.0"
      on "repository" as Input "project"
      and must establish "the delegated repository is clean"
      """js
      fact.workingTree === "clean" || fail("the delegated repository has local changes")
      """
```

Pour une mission inline, transmettre la table `missionDeclarations` suivante à `trust_plan_declarations_replace`, avec `plan`, l'`expectedRevision` de la dernière lecture du Plan et l'instantané complet des déclarations scalaires `declarations` (`{}` ici). Remplacer `assigned-repository` par le nom du répertoire du dépôt : un seul segment, sans séparateur de chemin. Définir `workspaceRoot` dans l'Environment comme son répertoire parent. Un tableau `operationSources` vide utilise les Operations installées ; y fournir les sources canoniques complètes lorsque la mission définit ses propres Operations.

```json id="dynamic-mission-declarations"
{
  "work": [
    {
      "id": "observe-repository",
      "rootInputs": {
        "repository": "assigned-repository"
      },
      "definition": {
        "kind": "inline",
        "procedureSource": "@trust-dsl:1 @procedure:documentation-observation @version:1.0.0\nFeature: Verify a delegated repository is clean\n  Background: Plan context\n    Given Procedure scope\n      | check | authorized | forbidden |\n      | all | Read the assigned repository. | Modify the repository or qualification criteria. |\n    And one reference \"repository\"\n  @scenario:observe\n  Scenario: Observe the repository\n    Then Check \"clean repository\" runs Operation \"git.head-read@1.0.0\"\n      on \"repository\" as Input \"project\"\n      and must establish \"the delegated repository is clean\"\n      \"\"\"js\n      fact.workingTree === \"clean\" || fail(\"the delegated repository has local changes\")\n      \"\"\"\n",
        "operationSources": []
      }
    }
  ]
}
```

Une mission publiée utilise plutôt `definition: { kind: "published", reference: "documentation-observation@^1.0.0" }` ; cette Procedure doit déjà être installée. Les références acceptent des versions SemVer exactes ou des plages standard. TRUST choisit la version la plus élevée satisfaisant le sélecteur avant de valider sa compatibilité et fige toute la composition récursive à l'acceptation. Les publications ultérieures ne modifient pas les missions acceptées. Les définitions inline restent dans l'historique persistant du Plan sans publier de versions réutilisables au catalogue.

Lire le Plan enfant obtenu et, lorsque le lancement est autorisé, transmettre son identifiant au worker affecté. Déclarer une mission ne lance pas d'agent : ce lancement reste à la charge de l'hôte. Le worker lit son enfant et transmet uniquement l'URI de Check fournie au Runner. Le coordinateur lit les états courants de l'enfant et du parent ; une réponse du worker ne suffit pas à satisfaire une Invocation. L'escalade d'un enfant bloque le travail dépendant et utilise la reprise existante par l'opérateur.

Les missions acceptées ne permettent que l'ajout. Conserver les identifiants, définitions et entrées racines acceptés inchangés lors d'un ajout. Une resoumission identique garde la même résolution et le même enfant ; supprimer ou modifier est refusé. Omettre `missionDeclarations` conserve les missions existantes. Un lot invalide est rejeté atomiquement avant toute création d'enfant. L'ajout de travail retire la qualification parente dépendante jusqu'à la fin du travail requis.

## Recette de l'extension de coordination

Le workflow PostgreSQL suivant est une recette d'intégration distincte. Sa demande conservée, la prise en charge par le worker et sa réponse ne remplacent pas les collections de missions ni le cycle de vie des Plans enfants du moteur.

La Procedure `agent-delegation` coordonne une mission délimitée. L'hôte lance l'agent. Une base PostgreSQL externe conserve les instructions et la réponse ; TRUST contrôle quand chaque Operation peut être exécutée et qualifie le résultat observé.

| Étape | Responsable | Résultat |
| --- | --- | --- |
| Créer la mission | Coordinateur | La demande, l'attribution, le résultat attendu et le périmètre sont conservés. |
| Prendre la mission | Agent désigné | La base enregistre la prise en charge et retourne les instructions. |
| Déposer la réponse | Agent | Le rapport et une issue terminée ou bloquée sont conservés. |
| Constater la fin | Coordinateur | TRUST qualifie l'issue enregistrée ; un blocage conduit à l'escalade. |

L'agent reçoit une URI de Check, lit le Plan et suit son intention courante. Après le travail, il déclare `response` et `outcome` par MCP avec la révision courante. Le Check de dépôt apparaît alors. L'agent l'exécute par le runner ; déclarer une réponse ne suffit pas à l'enregistrer dans la base externe ni à satisfaire le Check.

Si l'agent perd la sortie de sa prise en charge réussie, un nouveau client peut lire le Plan avec la même URI de Check. Le contexte d'engagement restitue les instructions, le résultat attendu et le périmètre immuables fournis à l'engagement ; ce ne sont pas de nouveaux Facts observés en base. Continuer avec l'intention courante et le prochain Check disponible, sans rejouer la prise en charge déjà satisfaite.

Une réponse bloquée enregistrée reste immuable. Un nouveau travail de reprise passe par une mission suivante avec de nouveaux identifiants de Plan et de mission, et une référence à la précédente. Reprendre l'ancien Plan n'autorise pas le remplacement de la réponse initiale.

L'identifiant d'une mission ne peut pas être réutilisé pour une autre demande. La prise en charge avec l'identité désignée et le dépôt d'une réponse identique peuvent être rejoués. Une réponse différente ne peut pas remplacer le premier dépôt. La base conserve les événements de création, de prise en charge et d'issue ; TRUST conserve les tentatives, les Facts acceptés, les qualifications et les intentions.

<Callout>
La fin signifie que l'agent a rendu et enregistré une réponse déclarée terminée. Ce n'est pas une vérification indépendante de son exactitude. Ajouter des Checks ou une Procedure de revue lorsque cela est nécessaire.
</Callout>

## Périmètre actuel

Cette première recette fonctionne sur un hôte local de confiance. Le nom d'agent déclaré permet de relier les travaux ; il n'authentifie pas l'appelant. Le périmètre en texte n'est pas une politique de permissions exécutable pour les autres capacités de l'agent. Le lancement des agents, la découverte des missions en attente et la reprise des processus de l'hôte restent en dehors de cette Procedure.

Le déploiement PostgreSQL de test ne possède pas de volume persistant : il survit au redémarrage des clients, pas au remplacement du pod. Conserver PostgreSQL et l'historique SQLite de TRUST avant d'en faire un stockage de production durable.

Le fichier `environments/trust-test/delegations/README.md` du dépôt contient les commandes d'installation, la première demande réelle et la recette d'acceptance publique. Cette première demande appartient à son Plan conservé : choisir de nouveaux identifiants pour un nouveau travail.
