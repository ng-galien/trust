---
title: "Delegating a mission"
summary: "Declare child missions and distinguish their execution from the coordination integration."
order: 5
---

A delegation has two parts: TRUST creates and follows a **child Plan**; an agent host assigns a worker to it. A child Plan existing in TRUST does not mean anyone has started work.

Take one task: check whether repository `repo-a` is clean. The parent Procedure owns the list of work. A child Procedure contains the Check that reads `repo-a`. The worker executes that Check with the Runner. TRUST decides from the observed Fact whether the child is validated; the parent can then continue.

| I want to… | Put this in the Procedure | What happens at runtime |
| --- | --- | --- |
| Delegate a known task | An Invocation of a published child Procedure | Engagement creates its child Plan with fixed Inputs. |
| Discover tasks later | A mission collection, such as `work` | The agent appends a mission; TRUST validates it and creates its child Plan. |
| Assign a worker | Use the agent host's dispatch mechanism after reading the child Plan | The worker receives that Plan identifier, scope and expected result. |
| Use the child's output | Mark an observed child role `returned` and map its Result in the parent Invocation | A validated child supplies the value; a message from the worker alone does not. |

## Follow one mission

1. **Reserve work.** The parent source below declares `missions "work" declared by agent`. Its Invocation waits for every accepted mission in that collection. An empty collection waits for work.
2. **Describe a task.** After reading the parent Plan, the coordinator calls `trust_plan_declarations_replace` with its current revision and a mission for `repo-a`. It supplies the child's root Input `repository` and either a published Procedure reference or complete inline sources.
3. **Read and assign.** TRUST creates the child Plan and returns it through the parent. The agent host gives its identifier, purpose, scope and expected Result to the assigned worker. This host action is separate from the mission declaration.
4. **Execute and observe.** The worker reads the child Plan and gives its supplied Check URI to the Runner. The Operation reads the repository; TRUST validates or rejects the Check from the returned Facts. The coordinator rereads the parent to see whether its Invocation can continue.
5. **Learn from new work.** If `repo-b` appears, append a new mission while preserving `repo-a` unchanged. An accepted inline Procedure and its Operations remain in Plan history; they become reusable catalog versions only after separate publication.

The parent's decisive lines are:

```gherkin fragment
And missions "work" declared by agent
Then Invocation "execute-work" runs each declared Procedure in "work"
  and must establish "the declared observations are complete"
```

Here is the small, **published-child** form of the mission declaration. It is the `missionDeclarations` part of `trust_plan_declarations_replace`; also pass the Plan identifier, its latest `expectedRevision` and the complete scalar `declarations` snapshot. The child reference must already be published.

```json
{
  "work": [
    {
      "id": "repo-a",
      "rootInputs": { "repository": "repo-a" },
      "definition": { "kind": "published", "reference": "documentation-observation@1.0.0" }
    }
  ]
}
```

Use the complete inline example below when the child method is created during the work. In that case, `procedureSource` contains the whole child source; `operationSources` contains complete sources only for Operations that are not already installed.

<Callout kind="rule">
TRUST owns child Plan creation, Check qualification and Result import. The host owns worker dispatch. Neither a worker's message nor a successful external command qualifies a Check.
</Callout>

## Dynamic mission collections

A Procedure can expose mission collections that an agent fills after engagement. TRUST validates each mission and pins its complete composition before creating its child Plan. Each child has its own Checks, Session and history. An empty collection waits for work.

<Details title="Complete parent, child and inline mission sources">

These complete Procedures declare the parent collection and its worker's executable Check. The worker requires the installed `git.head-read@1.0.0` Operation and a repository accessible to the Runner in a compatible Environment. The Check qualifies observed repository state, not the worker's report.

```gherkin procedure id="dynamic-mission-parent"
@trust-dsl:1 @procedure:documentation-missions @version:1.0.0
Feature: Govern declared repository observations
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all | Read assigned repositories. | Modify repositories or launch unassigned work. |
    And missions "work" declared by agent
  @scenario:work
  Scenario: Execute declared missions
    Then Invocation "execute-work" runs each declared Procedure in "work"
      and must establish "the declared observations are complete"
```

```gherkin procedure id="dynamic-mission-worker"
@trust-dsl:1 @procedure:documentation-observation @version:1.0.0
Feature: Verify a delegated repository is clean
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all | Read the assigned repository. | Modify the repository or qualification criteria. |
    And one reference "repository"
  @scenario:observe
  Scenario: Observe the repository
    Then Check "clean repository" runs Operation "git.head-read@1.0.0"
      on "repository" as Input "project"
      and must establish "the delegated repository is clean"
      """js
      fact.workingTree === "clean" || fail("the delegated repository has local changes")
      """
```

For an inline mission, pass the following `missionDeclarations` map to `trust_plan_declarations_replace`, with `plan`, the `expectedRevision` from the latest Plan read and the complete scalar `declarations` snapshot (`{}` here). Replace `assigned-repository` with the repository directory name: one segment, without a path separator. Set the Environment's `workspaceRoot` to its parent directory. Empty `operationSources` uses installed Operations; supply complete canonical Operation sources there when the mission defines its own.

```json id="dynamic-mission-declarations"
{
  "work": [
    {
      "id": "observe-repository",
      "rootInputs": {
        "repository": "assigned-repository"
      },
      "definition": {
        "kind": "inline",
        "procedureSource": "@trust-dsl:1 @procedure:documentation-observation @version:1.0.0\nFeature: Verify a delegated repository is clean\n  Background: Plan context\n    Given Procedure scope\n      | check | authorized | forbidden |\n      | all | Read the assigned repository. | Modify the repository or qualification criteria. |\n    And one reference \"repository\"\n  @scenario:observe\n  Scenario: Observe the repository\n    Then Check \"clean repository\" runs Operation \"git.head-read@1.0.0\"\n      on \"repository\" as Input \"project\"\n      and must establish \"the delegated repository is clean\"\n      \"\"\"js\n      fact.workingTree === \"clean\" || fail(\"the delegated repository has local changes\")\n      \"\"\"\n",
        "operationSources": []
      }
    }
  ]
}
```

</Details>

A published mission instead uses `definition: { kind: "published", reference: "documentation-observation@^1.0.0" }`; that Procedure must already be installed. References accept exact SemVer versions or standard ranges. TRUST selects the highest matching version before compatibility validation and pins the full recursive composition on acceptance. Later publications do not change accepted missions. Inline definitions remain persistent Plan history without publishing reusable catalog versions.

Read the resulting child Plan and, when dispatch is authorized, give its identifier to the assigned worker. Declaring a mission does not launch an agent: host dispatch remains outside TRUST. The worker reads its child and gives only its supplied Check URI to the Runner. The coordinator reads current child and parent states; a worker response alone cannot satisfy an Invocation. A child escalation blocks dependent work and uses the existing operator resume path.

Accepted missions are append-only. Preserve accepted IDs, definitions and root inputs unchanged when adding work. Identical resubmission retains the same resolution and child; removal or modification is refused. Omit `missionDeclarations` to preserve existing missions. Invalid batches are rejected atomically before child creation. Appending work withdraws dependent parent qualification until the required work is complete.

<Details title="How a child returns a verified Result">

Parent-to-child Inputs are explicit and fixed for each child generation. In the other direction, a child Procedure marks an observed role `returned`; the parent Invocation explicitly maps that Result to one of its own typed roles. The child does not write arbitrary parent variables or change the parent's immutable root Inputs.

```gherkin fragment
  # In the child Procedure's Plan context and producing Scenario:
  And one reference "revision" returned
  Then Check "read revision" runs Operation "git.head-read@1.0.0"
    on "repository" as Input "project"
    and materializes "revision" from field "headRevision"
    and must establish "the revision is observed"
    """js
    fact.workingTree === "clean" || fail("the working tree is not clean")
    """

  # In the parent Procedure's Plan context and child Scenario:
  And one reference "child revision"
  Then Invocation "observe child" runs Procedure "result-child@1.0.0"
    on "repository" as Input "repository"
    and materializes "child revision" from Result "revision"
    and must establish "the child observation is complete"
```

The compiler rejects an undeclared, non-returned, mismatched or multiply provided Result. A flat child Result can be mapped to an unscoped parent role; `on each` may map one Result per target through a matching `for each` parent role. Other Result parent topologies are not yet supported. For a declared mission collection, the parent target is an unscoped `many` role and each proposed child Procedure's Result contract is checked before that mission is accepted.

Only the **fully validated current child Plan** contributes its Result values. A changed validated observation replaces them in a new parent revision. If the child is requalified negatively, escalated, or its generation is superseded, TRUST withdraws the values and reopens dependent parent Checks; unrelated children retain their identities. `plan.read` exposes current `importedResults` with their child and generation provenance, and revisions retain their prior projections. No hook or independent Invocation qualification is involved.

</Details>

<Details title="Coordination extension (PostgreSQL)">

**Coordination extension recipe.**

The following PostgreSQL workflow is a separate integration recipe. Its stored request, worker claim and response do not replace core mission collections or child Plan lifecycle.

The `agent-delegation` Procedure coordinates one bounded mission. The host launches the agent. An external PostgreSQL database retains its instructions and response; TRUST controls when each Operation can run and qualifies the observed result.

| Stage | Responsible actor | Result |
| --- | --- | --- |
| Create mission | Coordinator | The request, assignment, expected result and scope are persisted. |
| Claim mission | Assigned worker | The database records ownership and returns the instructions. |
| Submit response | Worker | The report and a completed or blocked outcome are persisted. |
| Observe completion | Coordinator | TRUST qualifies the stored outcome; a blocker leads to escalation. |

The worker receives a Check URI, reads the Plan and follows its current intent. After doing the work, it declares `response` and `outcome` through MCP with the current revision. The submission Check then appears. The worker executes it through the runner; declaring a response alone does not persist it in the external database or satisfy the Check.

If the worker loses its successful claim output, a fresh client can read the Plan with the same Check URI. The engagement context restores the immutable instructions, expected result and scope supplied at engagement; these are not newly observed database Facts. Continue with the current intent and next actionable Check, without replaying the satisfied claim.

A persisted blocked response remains immutable. Further recovery work uses a new successor mission with new Plan and mission identifiers and a reference to its predecessor. Resuming the old Plan does not authorize replacing the original response.

The same mission identifier cannot be reused for another request. Claiming with the assigned identity and submitting an identical response are replay-safe. A different response cannot overwrite the first submission. The database retains creation, claim and outcome events; TRUST retains attempts, accepted Facts, qualifications and intentions.

<Callout>
Completion means that the agent returned and stored a completed response. It is not independent verification of the response's correctness. Use additional Checks or a review Procedure when that is required.
</Callout>

**Current boundary.**

This first recipe runs on a trusted local host. The declared agent name correlates work; it does not authenticate a caller. Scope text is not an executable permission policy for the agent's other capabilities. Launching workers, discovering pending missions and recovering interrupted host processes remain outside this Procedure.

The retained test PostgreSQL deployment has no persistent volume: it survives client restarts, not pod replacement. Preserve both extension PostgreSQL data and the core runtime history before treating this as durable production storage.

The repository's `environments/trust-test/delegations/README.md` contains setup commands, the first actual request and the public acceptance recipe. The supplied first request belongs to its retained Plan: choose new identifiers for new work.

</Details>
