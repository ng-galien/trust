The Procedure below fixes one Jira defect in one Maven project. Four Scenarios in a chain, one Check each; two Checks materialize a revision that later Checks reuse. Each numbered line is explained under the source.

```gherkin procedure id="mono-project-change" title="mono-project-change" marks="2,3,9,10,12,15,17,18,19,21,25,26,34"
# language: en
@trust-dsl:1 @procedure:mono-project-change @version:1.0.0
Feature: Fix one Jira defect in one Maven project

  Drives the correction of one Jira defect inside one Maven project, from a clean baseline
  to a verified revision: read the ticket, establish the baseline, verify the fixed revision
  and confirm the fix is committed.

  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all   | Change and verify only the declared project for the Jira defect. | Alter the Jira evidence, project baseline, or execution environment to make a Check pass. |
    Given one reference "jira issue"
    And one reference "project"
    And one reference "baseline revision" for "project"
    And one reference "fix revision" for "project"

  @scenario:issue
  Scenario: Read the Jira defect
    Then Check "issue" runs Operation "jira.issue-read" on "jira issue" as Input "issue" and must establish "the Jira issue is ready for correction"
      """js
      (
        fact.issueType === "defect" ||
        fail("the Jira issue is not a defect")
      ) &&
      (
        fact.workflowStatus === "todo" ||
        fail("the Jira issue is not ready")
      )
      """

  @scenario:baseline
  Scenario: Establish the project baseline
    Given scenario "issue" is validated
    Then Check "baseline" runs Operation "git.head-read" on "project" as Input "project" and materializes "baseline revision" from field "headRevision" and must establish "the project baseline is clean"
      """js
      fact.workingTree === "clean" ||
      fail("the project has uncommitted changes")
      """

  @scenario:fix
  Scenario: Establish the committed fix
    Given scenario "baseline" is validated
    Then Check "fix" runs Operation "git.head-compare" on "project" as Input "project" using "baseline revision" as Input "baseRevision" and materializes "fix revision" from field "headRevision" and must establish "the fix is committed after the baseline"
      """js
      (
        fact.comparedBaseRevision === context["baseline revision"] ||
        fail("the fix uses another baseline")
      ) &&
      (
        fact.commitsAhead >= 1 ||
        fail("the fix is not committed")
      ) &&
      (
        fact.workingTree === "clean" ||
        fail("the project has uncommitted changes")
      )
      """

  @scenario:verification
  Scenario: Verify the committed fix
    Given scenario "fix" is validated
    Then Check "Maven verification" runs Operation "maven.project-verify" on "project" as Input "project" using "fix revision" as Input "revision" and must establish "the committed fix passes Maven verification"
      """js
      (
        fact.verifiedRevision === context["fix revision"] ||
        fail("Maven verified another revision")
      ) &&
      (
        fact.verificationStatus === "successful" ||
        fail("Maven verification failed")
      )
      """
```

<Legend items={[
  <>**Procedure tags.** Exactly one <code>@procedure:</code> (a lowercase slug), one semantic <code>@version:</code>, and <code>@trust-dsl:1</code>. The optional <code>@intent-chaining</code> tag makes every engaged Plan carry a rotating agent intent.</>,
  <>**Title and description.** The title is copied verbatim; the free text under it is the description shown on the Procedure page and on its Plans.</>,
  <>**Plan context.** Exactly one <code>Background: Plan context</code>; it starts with the mandatory Procedure scope DataTable, then declares typed roles. See [Plan context](/docs/procedures/context).</>,
  <>**Procedure scope.** Its mandatory first DataTable declares prose boundaries for every Check and may add boundaries for an exact Check name. Both are shown to the agent.</>,
  <>**Plan input.** A role with no other source is given at engagement: <code>one reference "jira issue"</code>.</>,
  <>**Scoped role.** <code>for "project"</code> attaches the role to a parent role; here a revision belongs to one project. Nothing declares its source yet: it is materialized by a Check below.</>,
  <>**Scenario tag.** Exactly one <code>@scenario:&lt;slug&gt;</code> per Scenario, unique in the Procedure.</>,
  <>**Check sentence.** <code>Then Check "&lt;name&gt;" runs Operation "&lt;domain.action&gt;" on "&lt;role&gt;" as Input "&lt;input&gt;" … and must establish "&lt;success reason&gt;"</code>. <code>on</code> names the target and binds one Input. See [Scenarios and Checks](/docs/procedures/scenarios-and-checks).</>,
  <>**Qualification.** One <code>js</code> DocString attached to the Check; each guard is a typed condition followed by <code>|| fail(reason)</code>. See [Qualifications](/docs/procedures/expectations).</>,
  <>**Failure reason.** A string expression evaluated and returned only when its guard is false.</>,
  <>**Prerequisite.** <code>Given scenario "issue" is validated</code>: this Scenario's Checks are actionable only after that Scenario is satisfied.</>,
  <>**Materialization.** <code>and materializes "baseline revision" from field "headRevision"</code>: the value of a produced field becomes the value of a context role, for later Checks.</>,
  <>**Using.** <code>using "baseline revision" as Input "baseRevision"</code> binds a further Input; every required Input of the Operation is bound exactly once.</>,
]} />

## The shape of the document

```text
# language: en                                          optional (English only)
@trust-dsl:1 @procedure:<slug> @version:<x.y.z> [@intent-chaining]
Feature: <title>
  [free-text description]

  Background: Plan context                              exactly one
    Given Procedure scope                               mandatory DataTable
      | check | authorized | forbidden |
    Given|And one|many <type> "<role>" [source clause]  one role per line

  @scenario:<slug>                                      one per Scenario, unique
  Scenario: <title>
    [Given|And scenario "<slug>" is validated]          prerequisites first
    Then|And Check "<name>" runs Operation "<domain.action>"
        on [each|all] "<role>" as Input "<input>"
        [using [all] "<role>" as Input "<input>"]…
        [and materializes "<role>" from field "<field>"]…
        and must establish "<success reason>"
      """js
      <boolean expression> || fail(<string expression>)
      """
```

## Reading the graph

The same Procedure on its **Graph** tab: Scenarios as cards top to bottom in dependency order, solid links for `Given scenario … is validated`, dashed links for a value materialized by one Check and used by another. Selecting the Check `fix` shows what it needs (`baseline`) and what a new verdict on it would reset (`Maven verification`).

<Callout kind="tip">
  Long Check sentences read better on continuation lines — the source editor formats them (**Format source**) at `on`, `using`, `and materializes`, `and must establish`. The catalog sources above are one-line; both forms compile identically.
</Callout>
