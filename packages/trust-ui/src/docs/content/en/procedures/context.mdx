The `Background: Plan context` first declares the Procedure's action scope, then every value a Plan carries as typed, named **roles**. Checks and completed child Invocations can fill observed roles; neither changes immutable Plan inputs.

> The first DataTable defines the authorized and forbidden boundaries. Each following sentence declares one role, with its type, cardinality and source.

```gherkin fragment title="One role per line"
  Background: Plan context
    Given Procedure scope
      | check | authorized | forbidden |
      | all   | Change and verify only the declared project. | Alter the environment to make a Check pass. |
    And one reference "jira issue"
    And many reference "affected project" declared optionally by agent for "jira issue"
    And many reference "fix revision" for each "affected project"
    And one reference "acceptance project" fixed as "payment-acceptance"
```

## The sentence

```gherkin fragment
Given|And one|many string|number|instant|reference "<role>" [declared [optionally] by agent] [fixed as "<value>"] [returned] [for "<parent>"]… [for each "<parent>"]…
```

| Part | Rule |
| --- | --- |
| `Given` / `And` | either keyword after the mandatory scope DataTable; no further table or doc string |
| `one` / `many` | cardinality: a scalar, or a collection of the type |
| `string` `number` `instant` `reference` | the same four types as Operation Inputs and produced fields |
| `"<role>"` | free quoted name, non-empty, unique in the Procedure — a readable label (`"jira issue"`, `"fix revision"`), not an identifier |
| `declared by agent` | the agent supplies the value after engagement |
| `declared optionally by agent` | the agent may omit the value; when supplied, the same type and cardinality rules apply |
| `fixed as "<value>"` | the value is written here; only for `one string` or `one reference`; cannot be combined with `declared by agent` |
| `returned` | exposes a role produced by a validated Check or child Invocation as a Result of this Procedure; it cannot be an input, fixed value or agent declaration |
| `for "<parent>"` / `for each "<parent>"` | parent scope, see below; repeatable, combinable with the two clauses above |

## The five sources

The source of a role follows from its declarations and producing Check or Invocation. `returned` annotates an observed role; it is not a sixth source.

| Source | How | Filled | Example |
| --- | --- | --- | --- |
| **Fixed value** | `fixed as "<value>"` | by the Procedure itself | `And one reference "Kind cluster" fixed as "trust-test"` |
| **Agent declaration** | `declared by agent` | after engagement, by the agent, through the closed declaration operation | `And many reference "affected project" declared by agent for "jira issue"` |
| **Materialized field** | a Check of the Procedure `materializes "<role>" from field "<field>"` | by that Check, from one of its produced fields, once validated | `And one reference "baseline revision" for "project"` + `… and materializes "baseline revision" from field "headRevision"` |
| **Invocation Result** | an Invocation `materializes "<role>" from Result "<child role>"` | from the current, fully validated child Plan; withdrawn if it loses validation | `And one reference "child revision"` + `… and materializes "child revision" from Result "revision"` |
| **Plan input** | none of the above | at engagement, by whoever engages the Plan (root inputs) | `Given one reference "repository"` |

Engagement accepts **exactly** the Plan inputs — no fixed, declared or materialized role. Adding a `materializes` clause on a Check or Invocation turns a would-be Plan input into a derived role.

## Parent scope

`for "<parent>"` and `for each "<parent>"` attach a role to another role: a revision belongs to a project, a record time belongs to a document.

- The parent must be a declared role; parent relations form an acyclic graph.
- A role below an optional agent declaration must itself be declared optionally by the agent, or be materialized by a Check or Invocation. This prevents a required value from depending on a parent the agent may omit.
- `for "<parent>"`: one shared parent value. `for each "<parent>"`: one value per value of the parent — the relation keeps **which value belongs to which parent**. When a Check runs `on each "affected project"`, a `using "fix revision"` selects the revision of *that* project, not the whole collection — the selection follows the scope, never an array position.
- Two roles are in the **same scope** when one is `for each` the other, or when they share the same parents. Same scope is what allows a `many` role to feed a `one` Input under `on each`, a produced scalar to compare with `context["<many role>"]`, and a scalar field to materialize a `many` role.

```gherkin fragment title="From the aircraft departure Procedure: values scoped to one flight"
    Given one reference "flight"
    And one reference "aircraft" for "flight"
    And many reference "cabin item" declared by agent for "flight"
```

## What a role feeds

- **A Check target**: `on "<role>"` — one Check (`on "project"`), one Check per value (`on each "affected project"`), or one Check with the whole collection (`on all "…"`).
- **Other Inputs**: `using "<role>" as Input "<input>"` (`using all` for a collection).
- **A qualification reference**: `context["<role>"]` reads the value of a visible Plan role — see [Qualifications](/docs/procedures/expectations).

Types and cardinalities must match the Operation's Input at each binding: a `many reference` role cannot feed a `one` Input without `each`; a `string` role cannot feed a `reference` Input.

<Details title="Compiled roles" expert>
Each role compiles to `{ name, type, cardinality, source, parents: [{ role, each }] }` where `source.kind` is `plan-input`, `agent-declaration`, `fixed` (with `value`), `operation-field` (with Check and field), `invocation-result` (with Invocation and Result), or `plan-identifier` (the synthesised role `plan`, see [Scenarios and Checks](/docs/procedures/scenarios-and-checks)). A Result also has `returned: true`. The Procedure page lists Plan inputs in its inspector; a Plan's engagement form is generated from them.
</Details>
